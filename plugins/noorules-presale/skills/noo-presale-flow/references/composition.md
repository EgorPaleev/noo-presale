# Подбор и сборка пайплайна

1. Начни с запрошенных результатов и доступных входов. Проверь указанные пользователем файлы и ID запуска. Затем посмотри канонические документы и реализацию затронутой области. Сначала используй ближайшие совпадения по путям, названиям или ID. Открывай историю или карту маршрутов, когда этих данных недостаточно.
2. Если пользователь назвал пайплайн, открой его определение. Для явно названного маршрута с одним результатом сразу используй его контракт. Иначе предложи один подходящий вариант: проверь совпавший проектный пайплайн, затем именованный сценарий из [базы](../../../assets/knowledge/flows.json). Если ни один не покрывает нужные результаты, собери цепочку из подходящих [маршрутов](../../../assets/knowledge/task-index.md).
3. Для каждого запрошенного результата определи этап, его входы, зависимости и проверку. Если подходящий артефакт уже есть, используй его вместо повторного этапа. Если пользователь просит обновить артефакт, бери его за основу изменения. Засчитывай любой материал, который покрывает роль входа по содержанию. Если нужно, собери минимум из доступных исходников. Добавляй промежуточный этап, когда без него нет содержательного входа или проверки. Связанные этапы с общим анализом объединяй, когда разделение дублирует работу. Независимые ветки отмечай для параллельного запуска.
4. Покажи, почему этот вариант подходит, какие файлы уже готовы, что надо добавить и что зависит от чего. Предложи альтернативу только при существенном различии по объёму, риску или времени. Если запрос был только на рекомендацию, остановись после предложения. Если нужно выполнить работу, перейди к [согласованию](approval.md).

## Пресейл

При автоматическом режиме возьми `presale-full` из встроенной базы. Подбери состав выдачи по запросу. Если нужен отдельный результат, собери минимальную цепочку или передай готовые входы в `noo-presale-stage`. Следуй [единому регламенту](../../../assets/knowledge/base/presale/workflows/presale-playbook.md) для критериев каждого этапа.

- В полном комплекте оставь `presale-demo` после плана и проверь его на итоговой сверке. Демо может выполняться вместе со сметой. Если КП должно ссылаться на демо, добавь его как зависимость и вход этапа КП. Если пользователь ограничил выдачу, обнови граф и входы сверки.
- В полном комплекте исследование клиента идёт отдельной веткой параллельно с разбором. План ждёт записку исследования и использует её как контекст. Если компания ещё не определена, ветка выдаёт подтверждённый контекст, пробелы и вопросы. При наличии этих данных план продолжается. Исследование можно запустить самостоятельно. Находки становятся требованиями после подтверждения.
- Для комплекта партнёру оставь этап клиентских материалов, если требуется передать ему результаты для его КП. Для прогона только до сметы убери этап клиентских материалов и соответствующий вход и зависимость из сверки. Прими существующий бриф, план или другой результат как внешний вход после проверки по контракту. Удали этап, который этот файл заменяет, и обнови зависимости потребителей.
- Дай исполнителю проверку этапа вместе с его входами. При поправимом расхождении доработай его на этапе-источнике и пересобери зависимые результаты по изменённым входам. Черновик допускается как результат этапа и вход для зависимого черновика, когда доступных данных хватает. В итоговой сверке явно сохрани статус готовности материалов и условия завершения.

## Пайплайны проекта

По запросу «сохрани пайплайн под именем …» возьми названную или последнюю цепочку из этого диалога и сохрани её как `.noorules/pipelines/<id>.json`. Согласованная цепочка из прошлого запуска берётся из его состояния. Если под этим именем уже сохранена та же цепочка, укажи её путь. Для замены другого определения дождись разрешения. Определение можно хранить в Git и запускать в другой рабочей копии репозитория через `noo-presale-flow`. Дай этапам устойчивые ID и объявляй входы по их роли. Статусы, отпечатки, фактические пути и данные клиента относятся к конкретному запуску.

```json
{
  "title": "Демо по готовому кейсу",
  "when": "Есть согласованный функциональный кейс, нужен кликабельный прототип и его проверка",
  "steps": [
    {
      "id": "demo",
      "task": "prototype",
      "inputs": ["functional-case"],
      "output": "prototype"
    },
    {
      "id": "demo-review",
      "task": "prototype",
      "inputs": ["functional-case", "prototype"],
      "dependsOn": ["demo"],
      "output": "prototype-review"
    }
  ]
}
```

В `steps` используй поля `id`, `task`, `inputs`, `output` и при необходимости `optionalInputs`, `skill`, `dependsOn` и `goal`. Если `skill` не указан, подбери его по маршруту. Перед запуском проверь, что названия маршрутов и навыков существуют, входы определены, зависимости разрешаются и в графе нет циклов. Для автоматической рекомендации по обычному запросу ищи подходящее определение по имени, `title` или `when`. Достаточно прочитать несколько совпавших файлов.

## Повторное использование результатов

- Используй существующий кейс, решение, компонент, тест, демо или отчёт как вход, если он покрывает нужный шаг. Ссылайся на исходный файл. Если есть только часть результата, добавь недостающее к тому же материалу, когда это входит в согласованный план.
- Для результата прошлого запуска проверь статус, отпечатки файла и важных входов, затем сверяй объём с новым запросом. Изменившийся или предварительный результат используй как вводные с указанием ограничения либо проверь заново ту часть, которая нужна. Для принятого входа запиши путь и отпечаток в `externalInputs`. Источник из прошлого запуска можно указать в `sourceRun`.
- Когда результат предназначен для дальнейшей работы команды, укажи в плане его канонический путь и способ проверки. Используй существующее место для кода, тестов, демо и документации. Выдачу положи в папку запуска или по пути пользователя. Промежуточные результаты храни по правилам состояния. В итоговом ответе укажи точку входа, способ запуска или проверки и применимые ограничения.
